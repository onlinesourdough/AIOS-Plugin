# Evaluate Spec

Freeze the audit, accepted input and relevant source evidence. Use
[Spec](../SKILL.md) as the contract. Evaluate the result without
editing it; an ordinary mechanical edit does not require a Spec audit.

| Check | Pass evidence |
| --- | --- |
| Input maturity | Rough idea, developed brief, near-complete specification or existing change is identified; maturity is not mistaken for quality |
| Evidence dimensions | Intent, served party, proof/measurement owner, result/non-goals, sources, execution owner, authority/risk, interfaces, operation/recovery and unknowns are classified resolved, inferred, missing or conflicting with evidence |
| Source preservation | Canonical owner and accepted wording remain intact; only an authorized minimal patch or missing specification material was added |
| Facts before questions | Discoverable facts have been inspected; only the next material owner decision is asked |
| One gate | Exactly READY, REVISE or BLOCKED, with no unsupported Build route |
| READY contract | Outcome; proof and measurement owner; context links; repository/worker root; scope/non-goals; authority/risk; dependencies/handoffs; expected evidence; operation/recovery/Ship scope; lead goal representation, stable identity, concise current todo, accepted revision, current state, latest evidence/blocker, exact next action are present; launch contract and worker-goal linkage appear only for actual delegation |
| Lifecycle continuity | The accepted outcome persists through the same task and any authorized goal; no phase goal, premature completion, silent replacement or narrower substitute outcome |
| Tracking and goal state | [Tracking SOP](../../aios/references/lifecycle.md) supplies native plan call/readback or an explicit unavailable-tool file fallback; no duplicate live list. Carried goal request/objective and actual state are preserved separately; missing required activation holds Build. The canonical blocked/terminal fallback applies only after prior verified activation; pending acceptance stays pending. |
| Local invariants | Affected repository instructions, ownership and real launch/capability boundaries are respected |
| Consequential behavior | When the proposed change may materially alter a real-world outcome, use [Risky Changes](../../aios-risky-changes/SKILL.md) and carry its baseline/check, recovery, and evidence-gap result into the contract; routine edits do not select it |
| Proportionate construction | Rough input gains enough to build; a developed source is preserved rather than reformatted into a second brief |

Return PASS only when every required check has direct evidence. Otherwise return
FAIL, the material gaps and the smallest correction or hold. Include subject,
checkpoint, check results and next action. Missing proof cannot become an
assumption about authority or success. AIOS changes also need representative
behavioral execution; frontmatter validation does not prove readiness decisions.
