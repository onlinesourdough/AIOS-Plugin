# Context changes during ordinary work

Use when the owner confirms a lasting change, corrects a stored fact or names a
new authoritative source. Examples: a new customer relationship, a changed
working preference, a corrected scope or a source replacing an older one.
A speculative idea, quoted external claim or one-off task instruction alone is
not durable owner context. Do not turn every conversation into onboarding.

1. Identify the smallest confirmed meaning, source/date, scope and future use.
   Check existing relevant context for duplicates or conflicts. Load only that
   source; do not read the entire home or copy a customer dossier.
2. Use [curation](curation.md) to choose the owner: short orientation/source
   pointers in AIOS.md or routed context, durable preferences in MEMORY.md,
   verified access and existing authority in CONNECTIONS.md. External business
   facts stay in their canonical system; retain a route when needed.
3. Check supported AIOS_FORMAT, account, exact latest bytes and existing write
   authority. A normal update already covered by session/standing authority
   needs no fresh approval. Without it, prepare the exact small change for a
   decision. Do not infer customer-system writes, broader access or Git sync
   authority from the new fact itself. Independent repository work does not
   harvest owner context; repository workers hand proposed learning to the lead.
4. Apply only the authorized, unambiguous update, re-read it and report the
   meaningful change briefly. Material conflicts preserve both versions and
   need one focused decision. Reuse later source-backed facts from their owner.

If Git continuity is configured, the [Sync procedure](sync.md) governs any
actual push under existing authority. Context capture and remote delivery are
separate effects. The overview may refresh from saved files, but that view is
not a second copy or canonical source. No background listener or automation is
created by this method.
